{% comment %} The summary read one PIC at a time: a line per person, with each queue the page summarises as a pair of columns across it. Where the cards answer "how much is in this queue", the table answers "how much of each queue is whose" — the same figures, turned so that the comparison the reader of a seksi queue actually makes is the one along a row. Read across, a line is that person's whole load in time order once the last group is folded back to the front: the quarter behind them, the work in hand, and the two queues still upstream that will reach them. Every group is the same two columns — the tikets, and the rows behind them — so the eye can be moved sideways between them without relearning the layout. Ahead of the groups sits the one figure that is not a count: the Indeks Beban, which is those same rows weighted by how hard they are and how soon they land, and which the table opens sorted by. It is the answer to the question the columns only supply the evidence for — who is carrying the most. The splits run down the table rather than across it: under each PIC sits a labelled set of lines per dimension — the jenis tabel of the data, then the kategori wilayah of its ILAP — each set adding back up to the PIC's own line. That is what lets every group carry every split instead of only the first, and what keeps the table four groups wide however many kinds the reference tables hold. Those lines are shown by default, the detail being the point of the table, and the button in the card header folds them away for a reading that wants the totals alone. Two rows of headers rather than one: the top names the queues, the bottom the two columns each of them holds. Every column of that bottom row sorts the lines, as does the name itself; the lines all being on the page at once, the sorting is done where they are rather than asked of the server again. A PIC's detail lines follow their PIC through a sort, being that PIC's figures broken up rather than lines in their own right. `data-summary-sort` is what the table arrives ordered by — see SUMMARY_DEFAULT_SORT. Context (see the page's view): summary_sections: `{key, label, variant}` per group, in column order. summary_details: `{key, label, entries}` per dimension the lines detail, each entry `{name, hue}` in the order every breakdown reads, `hue` being the palette slot its dot is marked in. summary_section_keys / summary_section_variants: the same keys and variants comma separated, for the JS below. {% endcomment %} {% comment %} How the Indeks Beban is worked out, folded away until the ⓘ beside the column is clicked. It is out of the way because it is read once and then known, and it is on the page at all because a single number standing for a person's workload has to be able to account for itself — every figure below comes from the weights in views/quality_control.py, so editing one changes what the page says about itself and the two cannot drift apart. {% endcomment %}
Indeks Beban = Σ ( baris data × bobot jenis tabel × bobot kategori wilayah × bobot prioritas × bobot antrean )

Dihitung per tiket, bukan per baris ringkasan, lalu dijumlahkan per PIC. Jumlah tiket tidak ikut menimbang — pengendalian mutu dikerjakan baris per baris, sehingga satu tiket berisi sejuta baris sama dengan seribu tiket berisi seribu baris.
